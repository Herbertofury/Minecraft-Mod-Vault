## 2026-08-20 Mod Doctor, compatibility, and version-porting research expansion

Version 0.8.0 expands the product research memory to 154 curated sources, 92 detailed execution records, 163 unique runtime tool cards, and 9 reusable repair patterns. The machine-readable source of truth is `assets/mod-doctor-knowledge.json`; detailed capability/evidence records are in `knowledge/doctor-tools.json`; and the complete human-readable synthesis is `ULTIMATE-TOOLS-AND-PORTING-KNOWLEDGE.md`.

The research covers loader toolchains, mappings, remappers, decompilers, bytecode and API diffing, source transformations, multi-version and multi-loader builds, runtime bridges, provider APIs, reproducible modpack updates, crash/log analysis, runtime testing, profiling, NBT/world repair, protocol compatibility, publishing, and official format specifications.

The integration decision is evidence-based:

- use canonical loader build systems for source ports;
- use Mapping-IO/Tiny Remapper/Vineflower/Enigma/Parchment-class tooling to reconstruct and translate namespaces;
- use japicmp/Revapi/ASM/Recaf/OpenRewrite/Mixin tooling to prove and repair API drift;
- use Modrinth, CurseForge, and GitHub release metadata for identity, provenance, compatible files, dependencies, hashes, and release assets;
- use Packwiz/Ferium-style reproducible manifests and provider-aware update logic;
- use Sinytra Connector/Probe, Kilt, and related bridges only as runtime candidates whose actual compatibility must be proven;
- use DataFixerUpper, NBT Studio, Amulet, MCA Selector, Spyglass, and schema-aware validation for world/data work;
- use dedicated client/server launch, GameTest, HeadlessMC, fresh logs, and exact reproducer testing before retaining a repaired or ported artifact.

## 2026-08-20 Porting Lab and executable-repair research refresh

Version 0.9.0 revalidated the strongest current analysis, porting, compatibility, and pack-maintenance candidates against their primary repositories before wiring them into the Version Atlas and Porting Lab.

### New evidence and cross-check tools

- InterMed: https://github.com/jarettr/intermed
  - Read-only static analysis for mods, modpacks, servers, logs, resources, Mixins, security/SBOM, and performance evidence.
  - Reviewed as 0.1.4-alpha. Commands and output schemas may change; findings remain evidence, not automatic rewrites.
- modcrawl: https://github.com/SirCesarium/modcrawl
  - Rust CLI/library/FFI for loader identification, metadata, dependencies, classes, constant-pool search, Mixin targets, and duplicate classes.
  - Young project with limited adoption; the Vault uses it only as an independent JSON cross-check after pinning and fixtures.
- Modpack Inspector: https://github.com/Rearth/Modpack-Inspector
  - Desktop modpack inventory, dependency graph, provider enrichment, config ownership clues, and log-oriented inspection.
  - Heuristic unused-library or config relationships are never treated as automatic delete instructions.
- ModLens MCP: https://github.com/CreeperHost/modlens-mcp
  - Local metadata/class/Mixin/access-rule/decompiled-source index exposed through CLI and MCP, with embedded SQLite by default.
  - MCP/AI output is navigation assistance; exact bytecode and runtime evidence remain authoritative.
- ModpackResolver: https://github.com/iTrooz/ModpackResolver
  - Coarse comparison of selected-mod availability across Minecraft versions.
  - Availability does not establish loader, API, dependency, side, or runtime compatibility.
- Retromod: https://github.com/Bownlux/Retromod
  - Reviewed as a controlled binary/runtime transformation candidate, not a substitute for source-equivalent verification.

### Porting Lab evidence snapshot

The embedded `assets/version-atlas.json` is generated by `scripts/build-version-atlas.py` from retained official and primary metadata snapshots. The generated atlas contains 907 Minecraft version records and records each source snapshot by filename, byte size, and SHA-256. The release never silently queries an unrecorded “latest” coordinate while constructing an offline plan.

The implementation separates four things that are often incorrectly conflated:

1. artifact identification and static analysis;
2. exact original-environment reconstruction;
3. semantic source, API, mapping, resource, and data migration;
4. optional binary/runtime compatibility bridging.

A tool can be valuable in one phase without proving the others. Every plan therefore retains tool maturity, reason, guardrail, exact pins when available, ordered gates, and a target-specific runtime matrix.

### Executable repair boundary

The first automatic Doctor repair is restricted to complete SHA-512 equality. Filenames, duplicate mod IDs, class collisions, provider slugs, and fuzzy similarity are insufficient. Every applied move is revalidated against the plan, quarantined instead of deleted, receipt-backed, and restorable. This narrow boundary is intentional: it establishes a transaction and rollback substrate before broader dependency or binary repairs are allowed to execute.
