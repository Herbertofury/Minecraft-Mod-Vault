# Future Vanilla Backport control plane 2.6.4

## Purpose

Build one canonical future-vanilla compatibility provider instead of letting every converted mod privately copy the same later-Minecraft systems into its own JAR.

Ownership precedence is strict:

1. target vanilla;
2. exactly one installed external provider with proven feature ownership;
3. the canonical `futurevanillabackport` provider.

A consuming port may adapt to the capability, but may not become another owner of the same future-vanilla registries, behavior, data, resources, assets, networking, or persistence surfaces.

## Current 26.2 -> 1.20.1 catalog

Generated from the complete Vanilla Feature Atlas:

- 25,789 target-missing surfaces total
- 14,158 registry entries
- 6,293 data paths
- 2,772 resource paths
- 1,565 external assets
- 500 SoundEvents
- 501 sound definitions
- 584 surfaces currently have exact static ownership evidence in the imported Vanilla Backport 1.20.1 source inventory

`backport-feature-catalog.json` is the machine source of truth for this target/source pair.

## Surrender behavior

The canonical provider activates a feature only when target vanilla lacks it and no installed external provider has proven exact ownership. If an external provider owns the feature, the canonical provider surrenders it before registration. If two installed external providers both prove ownership, the resolver fails closed and reports the conflict rather than relying on mod load order.

## Capability modules

Raw atlas surfaces are grouped into logical feature modules before implementation. A module owns its complete dependency closure: behavior, registries, data/resources/assets, tags/recipes/loot, translations/subtitles, particles/game events, networking/codecs, persistence/data fixers, acquisition, worldgen, rendering/UI, and server/common behavior.

Use:

```text
mmv-devkit vanilla-atlas validate-capabilities \
  --catalog backport-feature-catalog.json \
  --manifest backport-capabilities.json
```

Before claiming a full backport release, require:

```text
mmv-devkit vanilla-atlas validate-capabilities \
  --catalog backport-feature-catalog.json \
  --manifest backport-capabilities.json \
  --require-complete
```

The current empty capability manifest intentionally does **not** pass the full-release gate; it is the clean starting point for implementation, not a fake claim that all 26.2 gameplay has already been ported.

## One-source multi-version development

`multiversion/` is generated by `mmv-devkit multiversion scaffold` and pins Stonecutter 0.9.7. The current matrix demonstrates one source tree across:

- 1.20.1 Forge + Fabric — Java 17
- 1.21.1 NeoForge + Fabric — Java 21
- 26.2 NeoForge + Fabric — Java 25

Keep ordinary code shared. Use small Stonecutter `//?` seams only where Minecraft or loader APIs actually differ. Build every affected matrix node in CI.
